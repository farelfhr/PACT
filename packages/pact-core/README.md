# PACT Core: typed candidates, provisional scenarios and offline provider port

Implemented scope: FR-AUT-001/002 structural types under `pact_core.domain`, using
only Python's standard library. Frozen entities contain immutable tuples. Closed
`from_mapping` methods reject missing/extra fields with `DomainValidationError`;
typed constructors reject wrong domain/enum types without coercion. Unsupported
constructor keywords raise Python's `TypeError`.

`ActorId`, `TenantId`, `ResourceId`, `RoleId`, `ResourceTypeId` and `RuleId` are
distinct logical fixture/policy names following accepted ADR-0001's ASCII
identifier grammar. They are not organization/project API IDs, authentication
proof, approval receipts or trusted fixture attestations. They do not replace
the scoped opaque wire-ID direction in `docs/DATA_MODEL.md`.

The reference-complete `DomainCatalog` checks declared roles/types/tenants,
ownership and explicit membership/share references. Cross-tenant membership and
sharing facts are permitted without granting access; primary tenant equality
does not invent membership or sharing. Rule selectors must also pass
`catalog.validate_rule(rule)`; standalone rule structure cannot know a catalog.
The accepted five relation signatures and read-only action/profile pairings are
validated. `Decision` is expected policy data; `ScenarioVerdict` only defines
observed-verdict names. No evaluator assigns decisions or verdicts here.

M1-02 adds `ContractBody`, `parse_contract`, `normalize_contract`, `canonical_bytes`
and `contract_digest` for FR-CON-001/FR-INT-002. A body is candidate policy data,
never approval proof. There is no authenticated approval service, fixture adapter,
policy evaluator, runner, networking, provider SDK, persistence or public adapter.
Logical `contract_id`/`project_ref` names are not registry wire IDs or access grants.

`parse_contract` and `ContractBody.from_mapping` enforce structural validity.
Normalization additionally rejects possible decision **or assertion-profile**
conflicts with `AmbiguousContractError` (`review_state=NEEDS_REVIEW`,
`code=POSSIBLE_CONFLICT`). Actors may hold multiple roles; ownership, membership
and sharing do not imply tenant equality. Only incompatible resource types or
complementary same/different-tenant conditions establish disjointness. A single
rule containing both tenant conditions raises `UNSATISFIABLE_RULE`. Agreeing
overlaps remain unchanged. Uncovered cases retain `on_unmatched=NEEDS_REVIEW`;
this check does not execute policy against fixtures or assign verdicts. Original
ADR V-02 remains structurally valid but now requires review at normalization,
per the developer's recorded clarification. Historical examples stay unchanged.

Accepted `pact-json-1` canonicalization binds **every required body field**:
ASCII keys sorted lexicographically, compact `,`/`:` separators, ordinary JSON
escaping, decimal integers, UTF-8 without BOM or trailing newline. All arrays,
including roles, declarations, sources, rules and conjunctions, retain order.
Whitespace/object-key order/ASCII escape spelling do not affect SHA-256;
content or array-order changes do. Rule order grants no priority. The digest is
64 lowercase hexadecimal characters. Original ADR example golden digest:
`3efd267a7de481b330a8641880f3ef1e7d7e48a8f93b545913503169ea1a29ab`.
Canonicalization always normalizes first; ambiguous input receives no digest.

The decoder accepts exact `str` or UTF-8 `bytes`, at most 65,536 bytes, depth at
most 16 containers including root. Duplicate keys (also escaped equivalents),
floating/exponent/nonfinite tokens, boolean/null versions, unsupported schema
or canonicalization, undeclared selectors and extra fields are rejected before
hashing. ASCII names are 1–96 characters; versions 1–2,147,483,647; roles/types
1–64 unique, source references 1–32 (repeats preserved), rules 1–64 with unique
IDs, predicates 1–8. All objects are closed. `format="yaml"` means the accepted
JSON-compatible text subset through the same JSON decoder; block YAML, tags,
aliases, includes and multiple documents are unsupported. No expressions run.
The Python mapping boundary also bounds traversal to 65,536 visited nodes and
limits string sizes before inspection, preventing repeated shared references
from expanding validation work without bound. This does not change valid bodies.

`schemas/contract-1.0.schema.json` describes structure with local `$ref`s and is
generated by pure `contract_json_schema()`. Its Draft 2020-12 `$schema` URI is
metadata; validation never fetches it. [JSON Schema numeric type semantics](https://json-schema.org/draft/2020-12/json-schema-validation)
do not capture textual float-token rejection; byte/depth/duplicate-key limits,
declared references, unique rule IDs and ambiguity checks also require the
decoder/domain normalizer. A generic schema-only pass is insufficient.
Artifact/generator equivalence and local references are tested; external schema
engine/meta-schema conformance has **NOT RUN**. Pydantic is explicitly deferred
by the owner in favor of this JSON Schema/standard-library deliverable; no
dependency was acquired or tooling ADR accepted.

M1-03 adds a reversible **untrusted lifecycle model**, tracing FR-CON-001/002
and the model boundary for AC-002. `UntrustedContractState` and
`UntrustedApprovalSnapshot` cannot establish authenticated review. The closed
candidate importer starts DRAFT and rejects approval/receipt/status extras.
`ContractStatus` models the PRD transitions: DRAFT -> NEEDS_REVIEW -> APPROVED
or REJECTED; APPROVED -> SUPERSEDED or DEPRECATED. All other edges, including
repeated statuses and reopening terminal states, fail. Transition calls require
the exact expected model revision and body digest; duplicate event names in
that model's history fail as replay. An APPROVED label requires a matching
snapshot with explicit **claimed** author/reviewer/reference/UTC time and
recomputed canonical digest. None of those claims authenticates a human.

Frozen snapshots retain exact immutable policy content, version, project and
sources. History is a consistency-checked tuple; deprecation/supersession keep
the earlier snapshot. `new_draft_version` requires the same logical policy and
project and the next contract version, returning a fresh DRAFT without mutating
the old model/history. Frozen Python objects prevent ordinary mutation; they
are not protected storage against hostile code, host administrators or reflection.

Every model/snapshot reports `is_authoritative=False` and
`require_authenticated_approval` **always raises** `ApprovalRequiredError`.
It exposes no positive approval path or test-harness token. Diagnostic snapshot
exports carry `kind=UNTRUSTED_APPROVAL_MODEL` and cannot be imported as policy.
This internal diagnostic format is not an accepted public receipt schema.
There is no authenticated APPROVED snapshot type, serialized receipt importer,
human identity/user-presence check, trusted clock/freshness/revocation, durable
nonce store, protected registry/audit, execution service or atomic transaction.
History copied or forked from an older model can be modeled again; every copy
still fails authenticated approval. Local duplicate-event/revision checks do
**not** prove durable replay protection, concurrent approval exclusion or audit
integrity. Those decisions remain in PROPOSED ADR-0003/M0-02 and later M2 work.
AC-002's real execution rejection **and audit write** and AC-003's real human
approval have NOT RUN and are not complete product acceptance criteria.

M1-03 tests enumerate all 36 transition pairs, stale/replayed/forked/transplanted
claims, edited content/digest/version, strict metadata, immutable history and
forged JSON. The fresh-process audit check includes lifecycle/snapshot modeling
and fail-closed approval. See `todo.md` EV-0015 for exact results and gates.

M1-05 adds a **PROVISIONAL parser-only scenario grammar**, authorized by the
developer as a scoped exception while M1-04 is BLOCKED. This is not acceptance
of ADR-0002, a real fixture/route registry, target scope or an execution API.
`pact_core.scenarios.parse_scenario(text, declarations)` requires JSON text or
UTF-8 bytes and a separately constructed `ScenarioDeclarations`. It returns
immutable `Scenario` data with `is_authoritative=False`; declarations also
report false. There is no interpreter, request sender, credential store,
fixture/session setup implementation, verdict evaluator or approval path.

The companion local schema is `schemas/scenario-1.0.schema.json`, with an
explicit provisional URN. Two examples under `tests/fixtures/scenarios` reference
the existing **unapproved candidate** policy by logical contract/project name,
exact version and canonical body digest. Names are M1-01 logical fixture IDs,
not the accepted future public wire-ID specification. The test catalog declares
synthetic seller A/B, order A/B and an `order-read` route with the literal
`orders` segment. These are mock declarations, not an implemented demo.

The closed operations are `fixture.setup`, `http.request` and
`fixture.teardown`. Exactly one setup comes first, at least one GET request
follows, and exactly one teardown comes last. All step IDs are distinct.
Setup references, request actor/resource/route/rule references and contract
identity/version/digest must match the supplied declarations. Route/resource
types, actor roles and expected decision/profile must agree with the referenced
candidate rule. **Predicate truth is not evaluated**: successful parsing proves
structural bindings, not scenario planning correctness or access authorization.
Actual policy matching, trusted complete fixture facts, independent session
authentication and genuine contract/scope approval remain separate gates.

Routes use `{"route_ref":"order-read","resource_ref":"order-b"}` nodes.
The declaration consists of 1–8 literal ASCII path segments, each 1–32
characters matching `[A-Za-z][A-Za-z0-9_-]*`, followed conceptually by a typed
ResourceId. The parser does not render a URL or resolve a host. Absolute URLs,
query/header/body/credential input, string interpolation (including the PRD's
illustrative `${fixtures...}` syntax), shell/Python/template operations and
undeclared paths are unsupported and rejected. No general expression engine
or denylist-based command execution is present. A future transport must still
enforce reviewed origin, DNS, redirect and SSRF defenses; this parser does not
claim those protections have been implemented.

Request assertions begin with an exact `decision` expected/profile node.
ALLOW then requires `intended_resource`; DENY requires both
`no_protected_resource_disclosure` and `no_protected_state_change`, in that
order, with the same typed resource reference as the request. Custom status
lists, omitted disclosure checks and profile overrides are rejected. These
nodes describe planned observations; no HTTP 403/404, disclosure/state-change
check or deterministic verdict has actually been executed here.

Provisional limits: 64 KiB input (including whitespace), container depth 16,
3–32 total steps, 1–64 unique setup actors/resources/routes, ASCII strings
and logical IDs of at most 96 characters, exact supported version `1.0`.
Contract versions are exact integers 1–2147483647; digests are 64 lowercase
hex characters. Booleans/null, floats/exponents/non-finite numbers, duplicate
JSON keys, extra properties, malformed UTF-8 and YAML are rejected. Nesting
is scanned before recursive JSON decoding. Errors omit submitted values.
`to_mapping()` returns detached JSON-compatible data for round trips; there
is no approved scenario hash/canonicalization scheme in this increment.

The generated JSON Schema is a structural companion: ordering, cross-references,
profile sequence and parser input bounds need Python validation. Its metaschema
URI is metadata and is never fetched; no external schema validator has run.

M2-01 adds the internal `pact_core.providers.ContractProvider` Protocol with one
operation:

```python
generate_structured_contract(request: GenerationRequest) -> CandidateDraft | GenerationError
```

`GenerationRequest` has a logical project reference and a nonempty requirement
of at most 8192 UTF-8 bytes. It selects no provider, destination, credential,
repository context or execution scope. Requirement text is untrusted data.
Logical project labels are the existing M1-02 vocabulary, not public wire IDs or
authorization proof; authentic project access and context filtering are later
application/interface responsibilities.

`FakeProvider(response=<JSON text or bytes>)` deterministically normalizes the
scripted output with M1-02 and requires its project to match the request. It does
not interpret natural language. Valid output becomes an immutable `CandidateDraft`
with fixed DRAFT status and `is_authoritative=False`, retaining the exact candidate
body. Descriptive adapter/model/prompt provenance is a claim, not identity, token
usage, consent or a review receipt. The fake uses `fake`, `offline-fixture`,
`m2-01-1` and an explicit synthetic flag. A digest or result cannot authenticate
approval; the existing approval guard still rejects it.

Malformed/unsupported output and privileged extras produce INVALID_OUTPUT;
possible rule/profile conflicts produce NEEDS_REVIEW; project disagreement
produces PROJECT_MISMATCH. Wrong request objects yield INVALID_REQUEST. These
are generation outcomes, not verification verdicts. Error messages contain fixed
diagnostics, never raw requirements, completions or caught exception strings.
Payload-bearing request/response/body fields are excluded from repr. This is
bounded diagnostic minimization, not the unimplemented general evidence redactor.

`FakeProvider(failure=FakeFailure.TRANSPORT)` and `FakeFailure.TIMEOUT` simulate
typed TRANSPORT_FAILURE and TIMEOUT without sockets, timers, retries, fallback,
SDKs, services or model calls. Exactly one response or failure is required.
The fake is immutable and has no mutable call history or global client. No I/O
occurs in imports, constructors or generation; fresh-process audit tests exercise
valid, malformed and failure paths while denying audited network/native/process,
SDK import and filesystem-write activity. This is not a live transport or host
sandbox guarantee.
